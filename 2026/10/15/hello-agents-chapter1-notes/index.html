Hello-Agents 第一章学习笔记：亲手拆开一个 Agent 的运转闭环

发表于2026-10-15|更新于2026-10-15|学习笔记
|总字数:4645|阅读时长:19 分钟|浏览量:

学完 Datawhale《Hello-Agents》第一章后，我把那个”查天气 + 推景点”的旅行助手逐行拆了一遍，并实测验证了几个容易想当然的地方。这篇记录我真正卡住过的点，尤其是 Agent 循环里那个”历史到底怎么传”的问题。

一、这一章在讲什么

第一章没有一上来讲理论，而是直接给你一个能跑的小 Agent：你问”北京今天去哪玩”，它自己决定先查天气、再搜景点，最后给出回答。

代码只有两百来行，但把 Agent 的四个基本部件都覆盖了：

部件 代码 职责
工具（数据获取） get_weather(city) 调天气 API，拿实时天气和气温
工具（联网搜索） get_attraction(city, weather) 用 Tavily 搜索，按”城市+天气”推景点
模型封装 OpenAICompatibleClient 封装大模型调用，可换任意 OpenAI 兼容服务
调度循环 for 循环 + 正则解析 让模型自己决定下一步调哪个工具，直到 Finish[...]

这四块组合起来，就是”能联网、能调工具、能自己决定下一步”的智能体雏形。

三、工具一：get_weather —— 调 API 拿数据

3.1 current_condition 到底是什么

current_condition 不是 Python 内置变量，也不是写死的魔法值，而是天气接口返回的 JSON 里约定的一个字段名。

流程是：

  1. requests.get(url) 发 HTTP 请求
  2. 服务器返回一段 JSON 字符串
  3. response.json() 把 JSON 字符串转成 Python 字典
  4. data['current_condition'] 读字典里对应 key 的值

两个要点：

  • 字段名必须和接口完全一致，大小写也一样，写错了就是 KeyError。
  • current_condition 对应的值是列表，所以要加 [0] 取第一条。为什么用数组？很多天气 API 会预留”多地点/多时段”的扩展，实际绝大多数情况只有一条数据。

3.2 两个 except 的分工

拆开看：

  • requests.exceptions.RequestException：网络层面失败——请求根本没拿到正常响应（断网、超时、404/500、返回的不是合法 JSON）。
  • (KeyError, IndexError)：请求成功了、JSON 也解析出来了，但数据结构不符合预期。
    • KeyError：字典里没这个 key
    • IndexError：列表是空的，[0] 越界

也就是说：

  1. 状态码是 500，不是 200，raise_for_status() 会报错
  2. 返回体是 text/plain 的纯文本，根本不是合法 JSON

所以城市名写错时，实际走的是第一个分支（RequestException），而不是第二个。(KeyError, IndexError) 在这个 API 上几乎不会触发——它更像一段防御性代码，防止未来接口行为变化。

更值得警惕的是这带来的误导：用户把城市名打错，本来是个输入错误，却被报成”查询天气时遇到网络问题”。异常分支的提示文案是程序员写的业务猜测，不是程序自动判断出来的——这句话是这段代码最该记住的地方。

（补充一个细节：requests.exceptions.JSONDecodeError 确实是 RequestException 的子类，继承链是 JSONDecodeError → InvalidJSONError → RequestException。所以上面的 text/plain 返回体就算不 raise_for_status，走到 response.json() 也会抛 JSONDecodeError 并被第一个分支捕获，结论一样。）

四、工具二：get_attraction —— Tavily 联网搜索

4.1 为什么要专门配一个搜索 API

get_attraction 要和 get_weather 配套：先拿天气，再按”某城市 + 某种天气”搜适合玩的景点。

如果用 requests 直接爬搜索引擎，你得自己解析 HTML、处理反爬、过滤广告，很麻烦。Tavily 是专为 AI 程序设计的搜索 API：给它一段 query，它联网检索、自动提炼总结，直接返回干净的 JSON，代码读 answer 字段就行。

代价是需要 API Key、按次数扣额度：

搜索深度 特点 消耗
basic 快、够用 1 credit
advanced 检索更多网页、更全面 2 credit

免费套餐每月 1500 额度，个人学习完全够用。

4.2 search() 的三个参数

  • query=query：等号左边是参数名，右边是你定义的变量。比如 query = f"{city} 在{weather}天气下最值得去的旅游景点推荐及理由"。
  • search_depth="basic"：搜索深度。
  • include_answer=True：让 Tavily 把结果总结成一段简短答案，返回里才会有 answer 字段。为 False（默认）时没有这个字段，只能自己拼 results 里的网页摘要。

4.3 .get() 与 [] 的区别

dict.get(key, default) 是安全取值：key 不存在时返回默认值（不传则返回 None），不会报错。而 dict[key] 在 key 不存在时直接抛 KeyError。

  • response.get("answer")：有 answer 且非空 → 直接返回总结
  • response.get("results", [])：拿结果列表，没有时给个空列表兜底，后面的 for 就不会因为 None 报错

f"- {result['title']}: {result['content']}" 里的 f 是 f-string，{变量} 会被自动替换成值。开头的 - 是 markdown 的无序列表标记，纯粹为了排版，对程序逻辑没有任何作用。

五、模型层：OpenAICompatibleClient

这个类的价值在于兼容性：用官方 openai SDK，只要对方提供 OpenAI 兼容接口，改 base_url + api_key + model 就能切换。DeepSeek、通义千问、本地 Ollama 都适用。

  • __init__：构造方法，创建对象时自动执行，把配置存成实例属性
  • system 角色设定身份规则，user 角色代表用户问题——这是 OpenAI 接口的固定格式
  • stream=False：非流式，一次性返回完整回答
  • response.choices[0].message.content：choices 是候选回答列表（默认 1 条），取第一条的文本

六、【重点】Agent 循环：今天最绕的地方

前面几块都是”零件”，这一节才是 Agent 的核心。我在这里卡了很久，单独写透。

6.1 为什么需要循环

大模型只会输出文字，没有执行能力。它说”我要查天气”，天气不会自己出现——得由你的程序解析出这句话，真的去调函数，再把结果喂回去。

所以流程必然是：

约定格式（ReAct 范式）：

  • Thought: 模型的思考
  • Action: 模型决定调用的工具
  • Observation: 工具返回的结果（由程序填写）

6.2 prompt_history 和 full_prompt 到底是什么关系

先看代码：

这是我卡住最久的地方。 关键要理解一个前提：

大模型 API 是无状态的。 每次调用都是一次独立的 HTTP 请求，服务端不记得你上一轮发过什么，也不记得模型自己说过什么。它每次都从零开始读你发过去的这段文本。

所以：想让模型”记得”之前发生了什么，唯一的办法就是每轮把完整历史重新发一遍。

用个比喻——想象你雇了一个顾问，他每次接电话前都失忆：

  • 笔记本 = prompt_history：只有一本，循环外创建，循环里只往里加、从不重置
  • 这次电话念出去的内容 = full_prompt：每次都要把笔记本从头到尾念一遍
位置 prompt_history 的内容 本轮 full_prompt
循环前 [①用户请求] —
循环1 L172 [①] ①
循环1 L184 [①,②Thought+Action]
循环1 L213 [①,②,③Observation]
循环2 L172 [①,②,③] ①\n②\n③
循环2 L184 [①,②,③,④Thought+Action]
循环2 L213 [①,②,③,④,⑤Observation]
循环3 L172 [①,②,③,④,⑤] ①\n②\n③\n④\n⑤

三句话总结：

  1. prompt_history 是账本：整场对话的流水账，累计、只增不减。每轮加 2 项（模型的输出 + 工具的观察）。
  2. full_prompt 是快照：在每轮开头把当时的账本拍成一段文本发出去。第 N 轮的 full_prompt = 前 N-1 轮的完整记录 + 最初那条用户请求，不含本轮即将产生的内容。
  3. 因此 full_prompt 必须每轮重算：本轮结束账本又变长了，不重算下一轮发出去的还是旧的。

6.3 那”之前的内容”不是一直在重复吗？

是，而且这是必须的。 但要区分两种”重复”：

  • ❌ 不是同一段话在账本里存了 N 遍。每轮 append 的都是新产生的内容，账本是一条线性增长的流水账，长度是 1 → 3 → 5 → 7。
  • ✅ 确实重复的是：每轮把账本全部念出去。循环 3 的 prompt 里必然包含循环 1、2 的全部内容。

为什么必须重念？因为顾问失忆了。不重念，模型就不知道天气已经查过了，会一遍遍重复调 get_weather。

代价：prompt 每轮变长，5 轮循环的总 token 消耗大致是 O(n²)。对话一长成本和延迟都会飙升——这正是后续章节「上下文工程」要解决的问题。

局限：历史全给了，模型也不一定用得好。我跑的时候观察到，模型有时会把完全相同的工具调用连着发两次，尽管上一次的 Observation 就在历史里。这说明光靠塞历史并不能保证模型不犯傻，所以才需要评测和更好的上下文组织。

6.4 为什么要在 L184 截断多余的 Thought-Action

大模型有时会一次预测多轮，把后面好几轮的 Thought+Action 一起生成出来。不截断的话，程序解析 Action 时会乱套。

正则拆解：

  • r'...'：原始字符串，正则推荐的写法，避免 \ 转义冲突
  • (Thought:.*?Action:.*?)：捕获组。.*? 是非贪婪匹配，尽可能少地拿字符
  • (?=\n\s*(?:Thought:|Action:|Observation:)|\Z)：正向预查（零宽断言）——它是”停止信号”，用于判断匹配到哪结束，但不会把这段内容抓进结果。意思是：遇到下一轮的 Thought/Action/Observation（前面可能有换行和空白），或者文本结尾（\Z），就停下来
  • re.DOTALL：让 . 能匹配换行。不加的话 . 遇到 \n 就停，多行的 Thought/Action 匹配不上

if truncated != llm_output.strip(): 这一步是先比较再替换——本来就只有一轮的话（截断结果和原文相同），就不做多余操作。

七、Action 解析：三个正则的分工

模型输出的 Action: get_attraction(city="南昌", weather="晴天") 要被拆成函数名和参数：

逐条：

  1. 判断结束：startswith("Finish") 判断 Action 是否以 Finish 开头（区分大小写）。re.match 从字符串开头匹配，\[ 和 \] 把正则里有特殊含义的方括号转义成普通字符。.group(1) 取第一个捕获组，即中括号里的答案。
  2. 取函数名：(\w+)\( 匹配”若干单词字符 + 左括号”，捕获组拿到括号前的函数名。
  3. 取参数字符串：\((.*)\) 捕获括号内的全部内容。注意 .* 是贪婪的，会一路匹配到最后一个 )。
  4. 拆参数：re.findall 扫描出所有匹配。(\w+) 是参数名，=" 匹配等号加引号，([^"]*) 里的 [^"] 表示”不是双引号的任意字符”，遇到 " 就停。返回 [("city","南昌"), ("weather","晴天")]，用 dict() 转成字典。

为什么先 search 再 findall，不直接 findall？

技术上直接对 action_str 做 findall 也能跑，但先切出括号内的 args_str 是为了限定匹配范围。

因为大模型经常”自由发挥”，可能在括号外面也写类似 xxx="yyy" 的内容：

先 re.search(r"\((.*)\)", ...) 只保留括号内，括号外的全部丢弃，杜绝误匹配。这是工具解析里很重要的防御手段：限定匹配范围，防止模型的额外输出把正则带偏。

同理，re.match 返回 None 时直接调 .group(1) 会崩，正式项目里应该包一层判断或 try-except。

八、闭环回顾

核心就是一句话：大模型无状态，所以每轮都要把账本从头念一遍；账本每轮都在变厚，所以 full_prompt 必须每轮重算。

  2. 异常处理的粒度：except Exception 一把抓虽然省事，但没法区分是网络问题、密钥失效还是额度耗尽。正式项目应该按层拆开，并且让错误提示文案和真实原因对应——就像 3.3 里那个”城市写错却报网络问题”的例子。

  3. O(n²) 的 token 增长：目前 5 轮循环无所谓，但任务一长就必须做上下文裁剪或摘要。这是后面章节的主题。

十、小结

第一章最值钱的不是那两百行代码，而是让你亲手体会到三件事：

  1. 工具是 Agent 的手：模型只会说，执行要靠程序解析它的输出。
  2. 循环是 Agent 的心跳：Thought → Action → Observation 反复滚动，直到 Finish。
  3. 历史管理是 Agent 的记忆：因为 API 无状态，每一轮都得把过去完整带上——这是后面所有”上下文工程”问题的源头。

理解了这三点，再去看更复杂的框架，会发现它们本质上都在回答同一个问题：怎么把合适的历史，在合适的时机，喂给一个永远失忆的模型。
